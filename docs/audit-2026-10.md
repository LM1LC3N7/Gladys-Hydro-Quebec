# Audit et proposition d'évolution — octobre 2026

Audit de `Gladys-Hydro-Quebec` à la version 0.1.6 (commit `f0561ee`, 8 octobre 2026) : structure,
maintenance, dépendances, sécurité, CI/CD, documentation. Suivi d'une veille sur les nouveautés de
Gladys et du forum communautaire, puis d'une proposition d'évolution orientée expérience
utilisateur.

Les corrections marquées **« corrigé »** sont incluses dans la même branche que ce document. Le reste
est une recommandation à arbitrer. La section 12 révise le plan après lecture du forum (9 octobre) et
liste ce qui a été réalisé ensuite.

## 2. Structure et architecture

- **Découpage clair** : `index.js` (cycle de vie Gladys), `src/devices/contract.js` (un appareil par
  contrat), `src/hydroquebec/` (process Python et traduction), `bridge/hq_bridge.py` (adaptateur
  `hydroqc`, ~280 lignes). Toute la logique métier Hydro-Québec reste dans `hydroqc` : c'est le bon choix.
- **Couplage à un attribut privé** : `hq_bridge.py` modifie `contract._hydro_client.web_session_expiry`
  pour forcer la resélection du contrat (correctif de la fuite de données entre contrats, 0.1.5).
  C'est documenté, mais une montée de version de `hydroqc` peut le casser sans erreur visible. Le test
  « import seul » de la CI ne le détecte pas. Il faudrait le remonter en amont (API publique de sélection
  de contrat). `hydroqc` n'a publié aucune version depuis la 4.2.6 (décembre 2025).
- **`index.js` n'est pas testable** : l'état est au niveau module et l'instanciation du SDK se fait à
  l'import. Recommandation : extraire la boucle de rafraîchissement dans un module (`src/poller.js`)
  avec dépendances injectées, et la tester comme `session.js`.

## 3. Qualité du code et tests

- `npm run lint` et `npm run format:check` : aucune erreur.
- `ruff check --select E,F,W,B,UP,SIM,S,BLE,ASYNC,RUF,PL` :
  - `bridge/hq_bridge.py` : seulement `RUF100`, un `# noqa: SLF001` inutile tant que la règle n'est
    pas activée.
  - `scripts/debug_bridge.py` : `S603`/`S607` (appel de `docker` via `subprocess`). C'est attendu pour
    un outil de développement local.
- **Tests** : 13 → **18** (ajouts : crash du process pendant une écriture, compteur de générations,
  redécouverte après redémarrage du bridge).
- **Non couvert** :
  - `pollContractDevice` (correspondance instantané → états) ;
  - l'orchestration de `index.js` ;
  - toute la logique de `hq_bridge.py`. Il n'y a pas de `pytest`, alors que les correctifs 0.1.4
    (période absente) et 0.1.5 (fuite entre contrats) mériteraient chacun un test avec des faux objets
    `hydroqc`.

## 6. CI/CD et release

**CI** (`ci.yml`) :

- **Corrigé** : chaque commit poussé sur une branche de PR lançait la CI **deux fois** (`push` et
  `pull_request`). C'est du quota Actions perdu. La CI tourne maintenant sur les PR et sur les push
  vers `main`.
- **Corrigé** : un nouveau commit annule le run précédent de la même PR (`concurrency`).
- **Corrigé** : permissions explicites `contents: read` (moindre privilège).
- Recommandation : ajouter `ruff` et `pytest` au job `bridge`.

**Release** (`release.yml`) : recommandations, pas de changement. Le pipeline est validé en
production et ne peut pas être testé à blanc.

1. **Ordre des étapes** : le commit qui change `docker_image` dans le manifeste est poussé sur `main`
   _avant_ que l'image soit construite. Pendant le build multi-arch (plusieurs minutes), et
   définitivement si le build échoue, une installation depuis GitHub échoue avec « Unable to pull
   image ». Il faudrait construire et pousser l'image d'abord, puis committer, tagger et publier.
2. La boucle de push vise encore la branche `claude/shared-conversation-ekuxqd`, vestige de la dérive
   de branche par défaut de la 0.1.1. Une fois `main` confirmée comme branche par défaut, retirer
   l'entrée et supprimer cette branche ainsi que `claude/ci-manifest-label-fix`.
3. Passer `inputs.bump` par une variable d'environnement plutôt que de l'interpoler dans le script
   shell (bonne pratique ; le risque est faible puisque c'est un choix fermé).
4. Les notes de release sont générées automatiquement et ne listent quasiment que des PR Dependabot.
   Or l'interface Gladys renvoie vers les GitHub Releases, et des utilisateurs demandent des notes
   lisibles (fil « Intégration externe : documenter les releases », 7 octobre). Recommandation : un
   `CHANGELOG.md` FR/EN orienté utilisateur, repris dans la release.
5. Optionnel : SBOM et attestation de provenance (`sbom: true`, `provenance: mode=max`).

## 11. Proposition d'évolution

Le contexte appelle une évolution en trois temps :

- les pointes reprennent le **1er décembre 2026**, et c'est là que l'intégration a le plus de valeur ;
- Gladys 5.1 vient d'ouvrir les widgets et les scènes aux intégrations ;
- le cœur prépare les contrats énergie avec Hydro-Québec comme exemple, mais son mainteneur s'absente
  en novembre-décembre.

### Phase 1 — « Prêt pour l'hiver » (avant le 1er décembre)

1. **Transitions de pointe à l'heure exacte.**
   - **Problème** : aujourd'hui, l'état des pointes n'est recalculé qu'au poll (toutes les heures par
     défaut). « Préchauffage en cours » ou « pointe en cours » peuvent donc basculer **jusqu'à 59 min
     en retard**. Une scène qui baisse le chauffage au début de la pointe réagit trop tard, et
     l'abonné perd des crédits.
   - **Solution** : le bridge renvoie l'agenda des prochaines pointes, déjà calculé par `hydroqc`
     (`next_peak`, `next_critical_peak`, `today/tomorrow_morning/evening_peak`, début du
     préchauffage). Node arme des minuteries locales qui publient chaque changement d'état à la
     minute près.
   - **Cadence** : interroger les données ouvertes Hydro-Québec toutes les 15 min entre 10 h 30 et
     15 h (heure de l'Est), quand les pointes du lendemain sont annoncées, avec un décalage aléatoire
     par installation. C'est la stratégie de `hydroqc-ha` 0.7, qui évite que tous les utilisateurs
     frappent l'API en même temps.
2. **Déclencheurs de scène** (`scene_triggers` et `publishSceneEvent`) :
   - `critical_peak_announced` : filtre par contrat (`source: "devices"`), variables début, fin,
     matin/soir et type CPC/Flex D ;
   - `preheat_started`, `critical_peak_started`, `critical_peak_ended`.

   Ils permettent des scènes impossibles aujourd'hui : « me notifier sur Telegram : pointe critique
   demain 6 h–9 h », « baisser les thermostats au début du préchauffage ».

3. **Consommation quotidienne juste et historique immédiat** (anomalie n° 4) :
   - publier avec `created_at` = la journée mesurée (`dateJourConso`), une seule fois par journée ;
   - à la première découverte, rapatrier les 30 à 90 derniers jours, pour que les graphiques soient
     remplis dès l'installation.

   L'ordre et le format exacts de `dateJourConso` sont à valider sur un vrai compte avant
   d'implémenter.

4. Monter `gladys_version` à `>=5.1.0` (nécessaire pour les déclencheurs de scène). Compromis : les
   instances plus anciennes ne verront pas la mise à jour. Elles ne sont jamais mises à jour
   automatiquement de toute façon.

### Phase 2 — Tableau de bord et diagnostic

5. **Widget « Pointes Hydro-Québec »**, avec le contrat choisi dans les réglages du widget :
   - état courant et prochaine pointe critique (date, plage horaire) ;
   - tuiles liées aux fonctionnalités (crédit cumulé et projeté), mises à jour en direct ;
   - liste des pointes à venir dans la saison.
6. **Widget « Facture en cours »**, avec des données que `hydroqc` fournit déjà sans être exposées
   aujourd'hui :
   - montant à date et facture projetée (`cp_current_bill`, `cp_projected_bill`) ;
   - jour x/y de la période ;
   - coût moyen du kWh ;
   - graphique de consommation quotidienne.
7. **Badge d'état par contrat** (`publishTransports`) :
   - `cloud` quand tout va bien ;
   - `unreachable` avec la raison quand le poll échoue ;
   - « dégradé » avec message pour une donnée partielle (« pas de période de facturation, coût
     indisponible »).

   Le diagnostic passe ainsi des logs à l'interface.

8. **Actions** :
   - « Rafraîchir maintenant » ;
   - « Importer l'historique » (choix du contrat avec `source: "devices"`, nombre de jours).
9. Nouvelles fonctionnalités, avec `keep_history` seulement là où un historique a du sens (Gladys 5.1.2
   signale les appareils verbeux) :
   - crédit gagné la veille (CPC) ;
   - jours d'hiver écoulés (Flex D) ;
   - prochaine interruption planifiée (`next_outage`).

### Phase 3 — Suivi énergie natif de Gladys

10. **Tableau de bord énergie** : publier la consommation par 30 min, avec `created_at`, à partir des
    données horaires d'Hydro-Québec (`get_hourly_consumption`). C'est le modèle déjà éprouvé par
    l'intégration Enedis, qui a elle aussi un jour de retard. Gladys calcule alors les coûts avec le
    contrat de l'utilisateur.
    - Alternative : publier un index cumulatif (PR #2922). Mais les états arrivant avec retard
      seraient comptés dans la fenêtre courante, sauf recalcul manuel.
    - Choix à valider avec le mainteneur sur le forum.
11. **Contrats énergie** (dès que la PR #3130 et le SDK correspondant sont publiés) :
    - déclarer la capacité `energy_contracts` avec des modèles Tarif D et Flex D ;
    - publier le calendrier `hq-critical-peaks` depuis les annonces de pointe de la phase 1.

    Gladys calcule alors le coût exact, prix de pointe Flex D compris. Le widget de prix courant et les
    scènes déclenchées par le prix fonctionnent sans code supplémentaire ici. La phase 1 prépare
    directement cette étape : l'agenda des pointes est la source du calendrier.

## 12. Révision après lecture du forum (9 octobre) et réalisation

La PR #3130 a été **fusionnée le 8 octobre** mais n'est pas encore publiée : Gladys est toujours en
5.1.4 et le SDK en 0.14.0, sans `gladys.energy.*`. Elle apporte, sans code côté intégration :

- le calcul du coût au cent près pour le Tarif D et Flex D ;
- un widget natif « Prix de l'électricité » (prix courant, palier, prochain changement) ;
- un déclencheur de scène « le prix change » et une condition « prix courant ».

**Abandonné** (doublon du natif) :

- les déclencheurs « début/fin de pointe » propres à Flex D : un passage en pointe est un changement de

**Reporté** :

**Réalisé dans cette branche** (indépendant de la sortie de Gladys) :

1. **Fuseau horaire** (anomalie n° 8) : le bridge épingle son process à l'heure de l'Est avant

2. **Consommation datée** (anomalie n° 4) :

3. **Préchauffage du Crédit hivernal** (anomalie n° 9) : uniquement avant une pointe critique.
4. **Transitions à la minute près** :
